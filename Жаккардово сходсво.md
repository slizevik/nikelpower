### 1. Чанкование текста (Chunking)
Процесс начинается с разбиения неструктурированного текста (например, PDF научной статьи) на фрагменты.
*   Метод: Вместо простого разбиения на фиксированное количество символов, источники рекомендуют использовать иерархический или лексический чанкинг [1, 2]. Документ представляется как структура: Документ → Глава → Секция → Параграф [2].
*   Оптимальный размер: Оптимальным считается параграф, так как он является «семантически связной единицей» [2]. В материаловедческих задачах средний размер чанка (описания структуры) составляет около 840-860 токенов [3]. Использование естественных структур документа позволяет избежать потери контекста, характерной для обычного RAG [4, 5].

### 2. Векторизация (Vectorization)
Векторизация в GraphRAG системах происходит параллельно для разных типов данных.
*   Применяемые модели: 
    *   Для научных терминов и сущностей в материаловедении используется специализированная модель mat2vec (unsupervised word embeddings) [6, 7].
    *   Для общих задач могут использоваться модели OpenAI, Gemini или локальные решения через Ollama [8, 9].
    *   Для извлечения контекстных эмбеддингов в материаловедении эффективно применяется MatSciBERT [10, 11].
*   Что векторизуется: Векторизуются как сами исходные чанки текста, так и отдельно извлеченные сущности и отношения между ними [12].

### 3. Извлечение сущностей (Entity Extraction)
Согласно пайплайну LightRAG и научным статьям по MKG, извлечение сущностей происходит после чанкования, но до (или в процессе) финальной векторизации самих сущностей для графа [13, 14].
*   Процесс: Текстовые чанки подаются на вход LLM (например, GPT-4, Llama 3 или специализированной модели Darwin) [15-17].
*   Логика: LLM одновременно выполняет задачи NER (распознавание сущностей) и RE (извлечение связей) [16, 18]. Она выделяет тройки (субъект-предикат-объект), которые затем проходят этап Entity Resolution (разрешение сущностей) для удаления дублей и нормализации через экспертные словари [19, 20]. Только после этого очищенные сущности могут быть векторизованы для эффективного поиска по графу [12].

### 4. Загрузка векторизованных сущностей в Neo4j
После того как сущности извлечены и нормализованы, они преобразуются в формат, пригодный для графовой БД.
*   Формат загрузки: Популярным методом является конвертация полученного JSON-графа в формат RDF/XML, который легко импортируется в Neo4j [21, 22]. Также поддерживается загрузка через CSV-файлы [23].
*   Структура в БД: Каждая сущность становится узлом (Node), а связь — ребром (Edge) с определенным типом (например, plays_for или has_property) [24, 25]. 
*   Traceability (Прослеживаемость): Важной деталью является привязка каждого узла и связи к DOI (идентификатору первоисточника), что позволяет системе возвращать точные ссылки на документы при ответе [23, 26].
*   Команды: Для записи данных используются Cypher-запросы, такие как CREATE для создания узлов и связей или SET для обновления их свойств (включая векторы) [27-29].

Жаккардово сходство (Jaccard Similarity) в контексте создания и развития графовых баз данных (в частности, MKG — Materials Knowledge Graph) применяется для прогнозирования связей (link prediction) и завершения графа (graph completion) [1, 2]. 

*   Оценка применимости материалов: Алгоритм используется для определения сходства между узлами «Материал» и «Применение» [2, 3]. Это позволяет находить новые потенциальные области использования для уже известных материалов на основе пересечения их свойств в графе [3].
*   Улучшенная метрика ($J_{mat}$): В источниках описывается модифицированная формула жаккардова сходства, которая учитывает веса ($w_i$) для различных атрибутов материала. Этот метод имитирует логику ученых-материаловедов: при поиске материала для конкретной задачи они сравнивают его химические и физические свойства с характеристиками материалов, уже зарекомендовавших себя в этой области [3].
*   Валидация: Более высокий балл модифицированного жаккардова сходства указывает на более высокую вероятность того, что материал подходит для целевого применения [3]. При этом в экспериментах отмечается, что сетевое сходство (network-based similarity) зачастую показывает более высокую точность прогнозирования, чем чистое жаккардово сходство [4, 5].

### Архитектуры графовых баз данных
В источниках упоминаются несколько ключевых архитектурных подходов и систем для реализации графовых БД:

1.  Neo4j: Это основная СУБД, используемая для хранения графов знаний (MKG, MekG, MGED-KG) [6-8]. Она поддерживает функцию сопоставления подграфов (subgraph matching), что позволяет выполнять сложные запросы на основе условий, введенных пользователем [6, 9].
2.  Лексический граф (Lexical Graph): Архитектура, используемая на этапе подготовки данных. Она представляет структуру документа в виде графа, где узлы — это иерархические элементы (документ → глава → секция → параграф), а ребра — отношения «предшественник», «последователь» или «родительский элемент» [10, 11].
3.  ESAMP (Event Sourced Architecture for Materials Provenance Management): Архитектура управления происхождением материалов, основанная на событиях. В ней последовательность экспериментальных шагов моделируется как направленный граф, где узлами являются образцы (Samples) и процессы (Processes), соединенные связями типа «Next» [8, 12, 13].
4.  Темпоральный граф (Temporal Graph): Реализованная в библиотеке Graphiti, эта архитектура позволяет хранить временные метаданные для фактов в графе [14, 15]. Она автоматически аннулирует старые факты (invalidated_at) при поступлении новой, противоречащей информации, сохраняя историческую запись изменений [16-18].
5.  Нативная графовая архитектура: Используется для хранения разнородных данных из рабочих процессов изготовления, измерений и моделирования, расширяя европейскую онтологию моделирования материалов (EMMO) [19, 20].

Для создания комплексных систем (например, Temporal RAG) эти архитектуры часто объединяются в гибридный пайплайн: FastAPI на бэкенде, Neo4j как хранилище графа и React для визуализации связей [21, 22].
